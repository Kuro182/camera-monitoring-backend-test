# Legacy

Исходный `CameraEventLoader` оставлен без изменений для сравнения, отрефакторенная версия находится в `CameraEventLoaderRefactored`

## Code review исходного метода

### Корректность

- Если общий диапазон не кратен 10 минутам, то последний запрос выйдет за  `to` и может вернуть лишние события
- Не проверяется корректность диапазона - `from > to`
- Исходный метод не проверяет, что `from` и `to` имеют одинаковый `DateTimeKind`
- Размер окна в 10 минут и минимальный `Confidence` 0.7 заданы магическими числами. Я вынес их в именованные константы

### Производительность

- Каждый 10-минутный интервал создаёт отдельный синхронный запрос. На большом диапазоне будет достаточно большое количество сетевых вызовов, которые могут перегрузить удалённый сервис
- Если WCF-сервис поддерживает большие диапазоны и приемлемый размер ответа, число запросов можно сократить
- Проверка дубликата в `HashSet` в среднем выполняется за `O(1)`, поэтому удаление дубликатов имеет сложность `O(n)`. Последующая сортировка — `O(n log n)`

### Работа с удалённым сервисом и ошибки

- `GetEvents` выполняет синхронную сетевую операцию и блокирует вызывающий поток
- В исходном методе отсутствует контекст ошибки: по исключению нельзя сразу понять, на каком временном окне произошёл сбой — добавил своё исключение
- Таймаут вызова должен быть ограничен в конфигурации WCF-клиента. Синхронный контракт не поддерживает `CancellationToken`
- Для временных ошибок с сетью возможен retry. Но после `CommunicationException` или `TimeoutException` WCF-канал может оказаться в состоянии `Faulted`, поэтому безопасный retry должен получать новый клиент через фабрику, а не повторно использовать тот же экземпляр

### Дубликаты

- Одно событие может повторно прийти от внешнего сервиса
- Событие на границе двух окон может попасть в оба ответа
- В переработанном методе уникальность определяется составным ключом `(CameraId, Timestamp)`, который хранится в `HashSet`

### Граничные условия после рефакторинга

- Для `from == to` пустой результат является ожидаемым
- Для `from > to` выбрасывается `ArgumentException`
- Последнее окно ограничивается значением `to`, поэтому запрос не выходит за общий диапазон

## Текущий объём рефакторинга

В `CameraEventLoaderRefactored` зависимость от `ICameraService` передаётся через конструктор
Конкретную регистрацию DI не добавлял, потому что в условии нет реализации WCF-клиента
Аргументы диапазона проверяются, размер окна и порог `Confidence` вынесены в именованные константы, последнее окно не выходит за `to`, добавлено исключение с границами проблемного интервала.
`null` вместо ответа рассматривается как пустой результат.
События дедуплицируются по `(CameraId, Timestamp)`, сортируются по `Timestamp` и потом по `CameraId`.
Retry пока не реализовывал, потому что для безопасного повторного вызова потребуется фабрика, создающая новый WCF-клиент

## Постепенная миграция

Я бы отделил работу с WCF от бизнес-логики и закрыл бы существующий клиент адаптером с понятным интерфейсом.
Поведение легаси-кода зафиксировал бы тестами, чтобы изменения не нарушили существующие сценарии.
После этого реализовал бы аналогичную загрузку событий в отдельном сервисе на современном .NET, сохранив совместимый контракт для потребителей. На переходном этапе старую и новую реализации можно запускать параллельно и сравнивать их результаты на одинаковых запросах.
Потом можем часть трафика направить в новый сервис и смотреть результаты, но иметь возможность быстро вернуться на легаси реализацию в случае ошибок новой реализации
